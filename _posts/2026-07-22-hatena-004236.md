## ETagについて

### S3 ETagを「データの一意性を保証するもの」と誤認

自動で、ETagが振られて、S3に保存したオブジェクトを一意に差別化してくれると誤認していた。

### キャッシュ制御を行うもの

> リソースの特定バージョンの識別子です。 これにより、キャッシュの効率が向上し、帯域幅を節約できます。コンテンツが変更されていない場合、ウェブサーバーは完全なレスポンスを再送信する必要がないためです。
>
> (出典: MDN Web Docs)

{% linkcard "https://developer.mozilla.org/ja/docs/Web/HTTP/Reference/Headers/ETag" %}

{% linkcard "https://tex2e.github.io/rfc-translater/html/rfc9110.html#8-8-3--ETag" %}

ETagは、キャッシュの確認をするために使用される識別子でした。  
コンテンツが変更されているかを確認することが可能。  
ETagが同じであれば同じものと認識してキャッシュを使用することが可能。

S3に振られているのも同じで、S3のオブジェクトのETagを確認することでブラウザに表示されている画像が変更されているか。また、キャッシュが存在しているかを確認することが可能。不必要なGET をしないで良くなる。

### マルチパートアップロードのETagの仕組み

1. クライアントが UploadPart で各パートを送ると、S3が各パートのMD5ダイジェストを計算し、それをそのパートのETagとして返す
2. 全パートアップロード後、CompleteMultipartUpload でパート番号とETagの一覧をS3に送る
3. S3は各パートのMD5ダイジェスト(バイナリ)を、パート順に連結する
4. 連結したバイナリ全体に対して、もう一度MD5を計算する(「ハッシュのハッシュ」)
5. 最後に -パート数 を付けて完成(例:3f5a9d8e1c2b7f4a6e9d0c1b2a3f4e5d-5)

{% linkcard "https://docs.aws.amazon.com/ja_jp/AmazonS3/latest/userguide/checking-object-integrity-upload.html#ChecksumTypes-Uploads" %}

このように単一であれば、クライアントから保存されるまでETagは変わらないため使えると思って誤認していた。マルチパートアップロードの際に値が変わるため間違いに気がついた。使い方が違う！

### ETagとMD5マッチング

| アップロード方式 | 暗号化方式 | ETag = MD5ダイジェスト? |
| --- | --- | --- |
| 単一パート | プレーンテキスト / SSE-S3 | 一致する |
| 単一パート | SSE-C / SSE-KMS | 一致しない |
| マルチパート | 暗号化方式に関わらず | 一致しない |

結論：条件によってはETagがMD5ダイジェストと一致し、AWS公式もその条件下での整合性検証利用を認めている。ただし、暗号化方式やアップロード方式によって条件が変わり、しかも見た目からは判断しづらい(コンソールや実装によっては16MB超で自動的にマルチパートに切り替わるなど)。そのため、条件を毎回正しく把握・維持し続ける必要があり、汎用的・確実な整合性検証手段としては向いていない

## MD5について

MP4のアップロードをおこなっていたため、自分が誤字ったと認識していたが、実際は全く別物だった。

MD5＝ハッシュ化・一意にするために使用

衝突攻撃に対する脆弱性が報告されているため、認証系のハッシュ化には使われていません。

{% linkcard "https://qiita.com/SDTakeuchi/items/821a32501312d5d0b13e" %}

一方、S3のオブジェクトアップロードのような『悪意ある第三者を想定しない、単なる転送破損の検知』用途では、衝突攻撃の脅威は当てはまらないため、MD5でも問題なく使用されています。

{% linkcard "https://repost.aws/ja/knowledge-center/data-integrity-s3" %}
